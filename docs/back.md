# АРХИТЕКТУРНАЯ СПЕЦИФИКАЦИЯ БЭКЕНДА
## Платформа активного обучения и полуавтоматической разметки «LBL_STDIO»
**Стек:** Python 3.11+, FastAPI, Ultralytics YOLO, OpenCV / LightGlue, SQLite, AsyncIO.

---

## 1. Архитектурные принципы и границы слоев (Clean Architecture)

В основе бэкенда лежит принцип инверсии зависимостей. Бизнес-правила не зависят от веб-фреймворка, базы данных или ML-библиотеки.

```
       ┌────────────────────────────────────────────────────────┐
       │                   Presentation Layer                   │
       │     FastAPI Routers, Pydantic DTOs, Static Mounts      │
       └───────────────────────────┬────────────────────────────┘
                                   │ вызывает
                                   ▼
       ┌────────────────────────────────────────────────────────┐
       │                   Application Layer                    │
       │       Use Cases (Оркестрация сценариев системы)        │
       │       Ports (Интерфейсы репозиториев и сервисов)       │
       └──────────────┬───────────────────────────┬─────────────┘
                      │ использует                │ реализуется через
                      ▼                           ▼
       ┌───────────────────────────┐ ┌──────────────────────────┐
       │       Domain Layer        │ │   Infrastructure Layer   │
       │  Сущности, Value Objects, │ │  SQLite, Local FS,       │
       │  Инварианты, Исключения   │ │  Ultralytics Adapter,    │
       │  (Чистый Python)          │ │  LightGlue Matcher, RTSP │
       └───────────────────────────┘ └──────────────────────────┘
```

### Правила взаимодействия слоев:
1. **Domain:** Не содержит импортов из внешних библиотек (нет FastAPI, нет SQLAlchemy, нет Torch/Ultralytics). Содержит правила валидации координат, состояния и бизнес-ошибки.
2. **Application:** Описывает сценарии (Use Cases) в терминах предметной области. Оперирует абстрактными интерфейсами (Портами): репозиториями и сервисами.
3. **Infrastructure:** Предоставляет конкретные адаптеры для абстракций: доступ к SQLite, сохранение файлов на диск, обертка над Ultralytics YOLO для обучения и инференса, OpenCV/LightGlue для сопоставления точек.
4. **Presentation:** Получает HTTP-запросы, маппит JSON/файлы в DTO, запускает Use Case и сериализует ответ в JSON или бинарный поток.

## 3. Спецификация ключевых сценариев приложения (Use Cases)

Каждый сценарий представляет собой независимый класс команды с единым методом входа (`execute`).

### 3.1. Блок разметки и верификации

#### `SaveAnnotationsUseCase`
* **Назначение:** Сохранение или обновление геометрии рамок кадра.
* **Вход:** `image_id`, список объектов рамок.
* **Алгоритм:**
  1. Валидировать, что координаты каждого бокса находятся в интервале $[0.0, 1.0]$.
  2. Проверить происхождение каждой рамки:
     * Если рамка создана вручную (`MANUAL`) $\to$ статус устанавливается в `VERIFIED`.
     * Если рамка получена от модели или точек $\to$ статус сохраняется как `PENDING_REVIEW` до явного подтверждения.
     * Если координаты автоматически предсказанной рамки были изменены человеком $\to$ статус автоматически переводится в `VERIFIED`.
  3. В рамках транзакции обновить аннотации кадра в БД.
  4. Пересчитать агрегированный статус кадра (`Image.status`).

#### `VerifyImageAnnotationsUseCase`
* **Назначение:** Экспресс-подтверждение всех гипотез на кадре («Approve All» по клавише `Space`).
* **Вход:** `image_id`.
* **Алгоритм:**
  1. Найти все боксы кадра со статусом `PENDING_REVIEW`.
  2. Перевести их в статус `VERIFIED`, зафиксировать текущее время верификации.
  3. Перевести статус самого изображения в `VERIFIED`.

---

### 3.2. Блок сопоставления ключевых точек (Keypoint Propagation)

#### `PropagateBoxViaKeypointsUseCase`
* **Назначение:** Перенос рамки с одного кадра на другой через поиск соответствий между особыми точками.
* **Вход:** `source_image_id`, `target_image_id`, координаты исходного бокса `source_box`.
* **Алгоритм:**
  1. Получить физические пути к файлам обоих изображений через `IFileStorage`.
  2. Вызвать порт `IKeypointMatcher`:
     * Кропнуть область исходного бокса на Изображении А (с небольшим контекстным отступом).
     * Вычислить ключевые точки и дескрипторы (SuperPoint / SIFT).
     * Вычислить точки целевого Изображения Б.
     * Запустить матчер (LightGlue / FLANN).
     * С помощью RANSAC отсеять выбросы и рассчитать матрицу преобразования (Homography / Affine).
     * Спроецировать полигон рамки на плоскость целевого кадра и вычислить охватывающий Bounding Box.
     * Рассчитать метрику надежности переноса (отношение количества согласованных точек к общему числу).
  3. Сформировать новую сущность `Annotation`:
     * `source` = `KEYPOINT_PROPAGATION`
     * `verification_status` = `PENDING_REVIEW`
     * Записать `source_annotation_id`.
  4. Вернуть спроецированный бокс клиенту для немедленной отрисовки.

---

### 3.3. Блок версионирования датасета

#### `CreateDatasetVersionUseCase`
* **Назначение:** Создание неизменяемого среза проверенных данных и сборка обучающих выборок.
* **Вход:** `project_id`, `augmentation_config`, коэффициенты сплита (Train/Valid/Test).
* **Алгоритм (с проверкой критического инварианта):**
  1. Запросить из базы все изображения проекта.
  2. **Human-in-the-Loop проверка:** Отфильтровать только те изображения, которые имеют статус `Image.status == VERIFIED`.
     * Если обнаружены кадры с `PENDING_REVIEW` боксами — исключить их или выдать предупреждение, что в датасет попадают **только подтвержденные данные**.
     * Если число проверенных кадров меньше минимального порога (например, 10) — выбросить ошибку доменного уровня `InsufficientVerifiedDataException`.
  3. Зафиксировать состояние аннотаций в сущности `DatasetItem` (иммутабельный снимок координат).
  4. Создать на диске структуру папок версии: `dataset/{version}/train`, `valid`, `test`.
  5. Сгенерировать аугментированные копии (Albumentations) для обучающей выборки в соответствии с `augmentation_config`.
  6. Сгенерировать текстовые метки `.txt` для каждого кадра и единый файл `data.yaml`.
  7. Перевести статус версии в `READY`.

---

### 3.4. Блок машинного обучения (Ultralytics Training & Inference)

#### `TrainModelUseCase`
* **Назначение:** Запуск обучения модели YOLOv8n на подготовленной версии датасета.
* **Вход:** `dataset_version_id`, гиперпараметры (число эпох, размер батча, базовая архитектура).
* **Алгоритм:**
  1. Убедиться, что версия датасета находится в статусе `READY`.
  2. Создать в БД запись `TrainingJob` в статусе `QUEUED`.
  3. Передать задачу воркера в асинхронный диспетчер задач (`ITaskRunner`):
     * Инициализировать экземпляр YOLO с базовыми весами (например, `yolov8n.pt`).
     * Запустить обучение с указанием пути к `data.yaml`.
     * Настроить Callback-функции Ultralytics: по завершении каждой эпохи считывать текущий лосс и валидационные метрики, обновлять поле `metrics_history` в `TrainingJob` для отдачи фронтенду в реальном времени.
     * По завершении сохранить веса `best.pt` в `storage/models/{version}/`.
     * Рассчитать финальные метрики: mAP50, mAP50-95, Precision, Recall.
     * Создать запись `ModelVersion` в статусе активной модели.

#### `BatchAutoLabelUseCase`
* **Назначение:** Разметка пула «сырых» картинок выбранной версией модели.
* **Вход:** `model_version_id`, список `image_ids`, `confidence_threshold`.
* **Алгоритм:**
  1. Загрузить указанную модель через порт `IModelPredictor`.
  2. Выполнить пакетный инференс по изображениям.
  3. Для каждого найденного объекта выше заданного порога уверенности:
     * Создать запись `Annotation` с параметрами:
       * `source` = `MODEL_PREDICTION`
       * `verification_status` = `PENDING_REVIEW`
       * `confidence` = фактическая уверенность нейросети.
  4. Выставить всем обработанным изображениям статус `Image.status = REQUIRES_REVIEW`.

---

### 3.5. Блок работы с потоковым видео (Active Learning Stream)

#### `ProcessStreamFrameUseCase`
* **Назначение:** Анализ кадра из видеопотока и отбор в датасет по правилу неопределенности.
* **Вход:** кадр из потока (бинарный буфер / NumPy массив), `stream_source_id`.
* **Алгоритм:**
  1. Получить активную модель проекта через `IModelRegistry`.
  2. Запустить быстрый инференс кадра.
  3. Применить **фильтр неопределенности (Uncertainty Sampling)**:
     * Проверить условие: есть ли на кадре детекции, чья уверенность попадает в окно сомнения $[Conf_{min}, Conf_{max}]$ (например, $0.70 \dots 0.90$).
     * Если условие не выполнено (модель либо полностью уверена $> 0.90$, либо ничего нет $< 0.70$) $\to$ кадр отбрасывается, ресурсы не тратятся.
  4. Применить **фильтр частоты (Cooldown)**:
     * Проверить время последнего сохраненного кадра с этого потока, предотвращая запись идентичных сцен.
  5. Если кадр прошел фильтры:
     * Сохранить файл на диск через `IFileStorage`.
     * Создать запись `Image` с источником `STREAM_INGEST` и статусом `REQUIRES_REVIEW`.
     * Сохранить предсказанные «сомнительные» боксы со статусом `PENDING_REVIEW`.

## 4. Спецификация контрактов и портов (Interfaces)

Разработчик реализует инфраструктурные адаптеры строго под следующие абстрактные контракты:

### Порты репозиториев (Data Access)
* `IProjectRepository`: Создание, чтение, получение счетчиков объектов.
* `IImageRepository`: Пакетная вставка, выборка по сплиту и статусу верификации, обновление статуса, получение неразмеченных изображений.
* `IAnnotationRepository`: Атомарная замена набора рамок изображения, массовое обновление статусов (`verify_all_by_image`), выборка исключительно верифицированных рамок для датасета.
* `IClassRepository`: CRUD справочника классов, контроль уникальности индексов `index_id`.
* `IDatasetVersionRepository`: Создание снимка, фиксация состава `DatasetItem`, чтение метаданных версий.
* `IModelVersionRepository`: Регистрация обученных моделей, смена активной модели для стриминга.

### Порты сервисов (Services & ML)
* `IFileStorage`:
  * Сохранение бинарного потока по относительному пути.
  * Получение абсолютного системного пути к файлу для передачи в библиотеки ML/OpenCV.
  * Удаление файла/директории.
* `IKeypointMatcher`:
  * Принимает два пути к файлам и координаты исходного бокса.
  * Возвращает спроецированные координаты бокса и скалярный скор согласованности точек.
* `IModelTrainer`:
  * Принимает путь к `data.yaml`, конфигурацию обучения и callback-обработчик прогресса.
  * Возвращает финальные метрики и абсолютный путь к сгенерированному `best.pt`.
* `IModelPredictor`:
  * Принимает список путей к файлам и порог отсечения.
  * Возвращает нормализованные координаты детекций, классы и степень уверенности.

## 5. Организация многопоточности и фоновых задач

Поскольку задачи машинного обучения (обучение YOLO, расчет LightGlue) и захват видеопотоков блокируют процессор или видеокарту, они изолируются от основного цикла событий FastAPI (Event Loop):

```
       ┌─────────────────────────────────────────────────────────┐
       │             FastAPI Main Async Event Loop               │
       │    (Обработка API запросов, веб-сокетов, CRUD в БД)     │
       └──────────────┬───────────────────────────┬──────────────┘
                      │ делегирует                │ опрашивает статус
                      ▼                           ▼
       ┌───────────────────────────┐ ┌───────────────────────────┐
       │     ProcessPool / GPU     │ │    RTSP Daemon Thread     │
       │    Ultralytics Training   │ │  Постоянный захват кадров │
       │    LightGlue Matching     │ │  сэмплинг по таймеру      │
       └───────────────────────────┘ └───────────────────────────┘
```

1. **Обучение нейросети:** Запускается в отдельном системном процессе (`multiprocessing` или отдельный воркер) во избежание захвата GIL и падения сервера по OOM (Out Of Memory). Прогресс обучения пишется в SQLite или общий потокобезопасный буфер.
2. **Keypoint Matching:** Так как инференс по двум картинкам занимает 50–200 мс, операция выполняется через `asyncio.to_thread` / `ThreadPoolExecutor`, не блокируя обработку веб-запросов других пользователей.
3. **Захват видеопотока:** Демон на базе `threading.Thread`, непрерывно считывающий кадры из `cv2.VideoCapture` и передающий анализируемый кадр раз в $N$ секунд в Use Case активного обучения.

## 7. Обработка ошибок и валидация

Архитектура использует централизованный перехват исключений через FastAPI Middleware:

1. **`DomainValidationException` $\to$ HTTP 422 Unprocessable Entity:** Ошибки выхода координат за пределы $[0, 1]$, отрицательные размеры рамок.
2. **`UnverifiedDataException` $\to$ HTTP 400 Bad Request:** Попытка включить неподтвержденные аннотации или изображения со статусом `REQUIRES_REVIEW` в сборку датасета.
3. **`ResourceNotFoundException` $\to$ HTTP 404 Not Found:** Отсутствие запрашиваемого кадра, модели или проекта.
4. **`ModelExecutionException` $\to$ HTTP 500 Internal Server Error:** Сбои при инициализации CUDA, чтении поврежденных весов или нехватке памяти при инференсе.
